# Peras on the local testnet — `vanilla` scenario run report

This report shows an analysis of the testnet smoke test that goes through the Peras functionality and checks that we are able to observe the desired behavior.

The report is generated by reading node logs.

| 2 | SPO with a key votes when eligible (persistent / non-persistent) | **Pass** |

* The node that did have the round‑6 cert (node5) kept trying to include it in

## 3. How the properties were checked

* **Per‑node voting controller**: `<pid>_vote.log` lines
  `TracePerasVotingRulesDecision`, `TracePerasVotingNotAVoterInRound`,
  `Ticked vote`, `Failed to read Peras pool ID…`.
* **Vote/cert DB**: tracer JSON events `ChainDB.PerasVoteDbEvent.AddVote`
  (result, `voteId`, vote weight) and `ChainDB.PerasCertDbEvent.AddCert`
  (round, result). `AddVote` is emitted on every node for every vote it stores,
  regardless of where the vote originated.
* The origin of a vote is the node whose seat index it carries. Vote latency =
  time the vote reached node *B* minus time it was added at its origin (all
  nodes run on one machine, so clocks are comparable).
* No `ObjectDiffusion*` events are in the logs, so diffusion is inferred from the DB events.

## 4. Results per property

### 4.1 Non‑SPO node without a key skips rounds — pass

node7 and node8 (relays) have no `PERAS_POOL_ID` / `PERAS_PRIVATE_KEY`
(`cardano-testnet` passes Peras options only to pool nodes). Each logged
`Failed to read Peras pool ID from environment` 5 250 times (every slot), has
zero `RulesDecision`/`Ticked vote` lines, and never forged a vote. They still
received all 46 votes and the certs (see 4.5), so a keyless node is a pure
observer.

### 4.2 SPO with a key votes if eligible — pass

Rounds where the voting rules allowed a vote: 0–6 and 55–57 (10 rounds).

| Node | Seat | Rounds in which it forged a vote |
|------|------|----------------------------------|
| node1 | 0 (persistent) | 0–6, 55–57 (10/10) |
| node2 | 1 (persistent) | 0–6, 55–57 (10/10) |
| node3 | 2 (persistent) | 0–6, 55–57 (10/10) |
| node4 | 3 (persistent) | 0–6, 55–57 (10/10) |
| node5 | 5 (non‑persistent) | 1, 2, 5, 6, 56 (5/11 decisions) |
| node6 | 4 (non‑persistent) | 1 (1/10) |

The 46 forged votes (4×10 + 5 + 1) are exactly the 46 `AddVote` events seen on
every node.

### 4.3 Node with a key skips voting if not eligible — pass

node5 and node6 log `TracePerasVotingNotAVoterInRound` in every round where
the rules said "vote" but the lottery did not select them (node5: rounds 0, 3,
4, 7, 55, 57; node6: 0, 2–6, 55–57). Every such round produced no vote.

Current scenario has no node that holds a key but is not an SPO in the committee, so that exact case is not exercised. Eligible‑vs‑ineligible is only tested with low‑stake non‑persistent candidates.

### 4.4 Non‑persistent voters change in time — good

The single non‑persistent seat was won by seat 5 (node5) in rounds 1, 2, 5, 6,
56 and by seat 4 (node6) in round 1 (both won in round 1). So both candidates
do vote.

### 4.5 Votes are diffused — pass

* All 8 nodes (including the relays) recorded exactly the same 46 distinct
  `(round, seat)` votes.
* Latency from origin to the other 7 nodes (322 samples): median 12 ms,
  p95 27 ms, max 34 ms for 315 of them.
* One outlier: the round‑6 vote of seat 0 (node1) reached the other 7 nodes
  53.8 s late (122.97 s at node1, 176.76 s elsewhere), at the same instant the
  other nodes switched to node1's fork (`SwitchedToAFork` at 176.77 s). See 5.1.

### 4.6 Certificates are generated at quorum — pass

On every node, in every round, `AddedPerasVoteAndGeneratedNewCert` was
returned exactly for the vote that took the accumulated weight from below to
at‑or‑above 0.77 (= 3/4 + 1/50); no vote crossed the threshold without
generating a cert, and none generated one without crossing. Example round 0:
seats 0, 2, 3 give 0.6875, seat 1 pushes it to 0.9375 → cert. Votes arrive in
a different order at each node, so the generating vote differs per node, as
expected. Certs were generated in rounds 0–6 and 55–57.

### 4.7 No second cert generation — pass

At every node, each of the 10 rounds has exactly one cert‑generating vote
(80 events in total); later votes of the same round return
`AddedPerasVoteButDidntGenerateNewCert`. At CertDB level 4 duplicate adds were
reported as `PerasCertAlreadyInDB` in round 56 (node3, node4, node6, node8) —
a cert arriving from a second path — and were correctly ignored.

### 4.8 Certificates are diffused — not shown

Every node generates every cert locally from the votes it receives, so the
`AddCert` events (all 8 nodes within ≈ 20 ms for rounds 0–5, 55, 56) cannot
distinguish "generated locally" from "received". The only observable
evidence is negative: the round‑6 cert existed at node5 only and never reached
the other nodes (5.1), which suggests cert diffusion did not deliver it. To
check this property properly we need either the `ObjectDiffusion` traces or a
scenario where a node is prevented from seeing votes (e.g. a partition).

### 4.9 The network goes into cooldown — pass

All 8 nodes' voting controllers moved to `NoVote` from round 7 (node5 from
round 8): VR‑1A requires the latest seen cert to be from round r‑1, but the
latest cert seen was round 5 (`VR1A := 7 == 6` false) and VR‑2A/2B did not
hold yet. No node voted in rounds 7–54 (47–48 rounds, ≈ 126 s → 990 s).
Cause: see 5.1.

### 4.10 Recovery from cooldown — pass

Recovery needs VR‑2A (last cert at least R = 20 rounds ago → from round 26)
and VR‑2B (round ≡ round of the last on‑chain cert, here 5, modulo K = 50 →
round 55). In round 55 all 6 keyed nodes took the VR‑2 path
(`VR2B (PerasRoundNo 1) := 55 > 5 ∧ 5 == 5`) and voted; rounds 56 and 57 went
back to the VR‑1 path; certs were formed in rounds 55, 56 and 57. The test
ran just long enough to see this (the log ends 3 rounds after recovery).

## 5. Unplanned observations

### 5.1 Stale cert inclusion produced invalid blocks

node5 evaluated "include cert of round 6" 1 571 times (once per slot) and put
it into the blocks it forged at 263 s, 306 s and 456 s
(`Forge.Loop.ForgedInvalidBlock`). Every node rejected those blocks:
`PerasEpochContextNotFoundForRound (PerasRoundNo 6) … not within current epoch
context bounds [12,16) / [16,20) / [24,28)` — a cert older than the previous epoch can
no longer be validated, but the inclusion rules still offered it.

### 5.2 Epoch‑boundary inclusion errors

Nodes 1–6 each logged 337–344 `TracePerasCertInclusionError` entries, e.g.
`round 4 not within current epoch context bounds [0,4) … no previous epoch
context available because Peras isn't enabled`, i.e. around the first epoch
boundary the inclusion code asks for an epoch context that does not exist
yet. This is a known error that happens because at the beggining of the era we need to tick into the block to get an information about the context. But it's not possible if the block has not arrived in time (normal behaviour). This problem is being fixed as a part of Peras v1 to the mainnet project.

## 6. Changes made specifically for the test

All of this is in the working trees under `devenv/` (`ouroboros-consensus`
branch `qnikst/testnet`, `cardano-node` branch `qnikst/peras-testnet`). The run
used the **uncommitted** modifications listed below (the logged parameters
match them), so commit them before treating the run as reproducible.

### 6.1 Cooldown / ignorance period

`Ouroboros.Consensus.Peras.Params` (`defaultPerasParams`):

| Parameter | Upstream value | Test value | Mechanism |
|-----------|----------------|------------|-----------|
| `perasCooldownRounds` (K) | 1928 | 50 | `PERAS_COOLDOWN_ROUNDS` env, default 50 (first 100) |
| `perasIgnoranceRounds` (R) | 487 | 20 | `PERAS_IGNORANCE_ROUNDS` env, default 20 (first 40) |
| `perasCertMaxRounds` | 487 | 20 | = ignorance rounds |
| `perasTargetCommitteeSize` | 800 | 5 | `PERAS_TARGET_COMMITTEE_SIZE` env, default 5 (first 2) |
| `perasCertArrivalThreshold` (X) | 30 | 80 | hard‑coded (30 → 60 → 80) |

The env variables are read through `unsafePerformIO` CAFs (marked "TEMP HACK").
They were not set in `launch.sh`, so the defaults applied.

### 6.2 Round in which the vote is cast

`NodeKernel.perasVoteForgingController`: upstream votes only when
`slotInRound == 0`. The test votes only at `slotInRound == 75`. The comment says: late enough that the
epoch has blocks, early enough for votes/certs to diffuse; the 0.2 s slots.
X = 80 and the vote slot 75 are coupled: a cert for round r must arrive within 80 slots of the round start to satisfy VR‑1A, and the vote is cast at 75.

### 6.3 Rule change

`Voting/Rules.hs` `perasVR1B`: the check that the candidate block extends the
latest seen cert is replaced by `Bool True` (original line commented out). This problem happened due to the bug in the certificate db logic, the problem was already fixed upstream.

### 6.4 Tracing

Currently tracing mechanism is refactored by the consensus team. Before that refactoring will be complete Peras team introduced a number of fixes to observe events.

1. **File side‑channel** (`NodeKernel.hs`): `traceM_vote` appends
   `show`‑ed events to `<pid>_vote.log` in the node's working directory via
   `unsafePerformIO appendFile`. A global `MVar` lock was added (uncommitted)
   to stop concurrent writers interleaving. It records the voting controller
   events (`RulesDecision`, `NoVoteAfterFirstSlotInRound`, `NotAVoterInRound`,
   epoch context resolver dump, forged vote, add‑vote result, cert chain‑sel
   outcome), startup lines, the missing‑key error, and (uncommitted) cert
   inclusion decisions (`IncludeCert`, `PastHorizonException`,
   `InclusionError`). It needs `unix` and `recover-rtti` in the cabal file
   (marked FIXME: remove).
2. **Vote content in the DB trace**: `AddPerasVoteResult` now carries the
   `ValidatedPerasVote` in all three constructors, so `PerasVoteDbEvent.AddVote`
   shows the vote, seat, proof type and weight (previously none of this).
3. **cardano-node** (`cardano-node/.../Tracing/Tracers/ChainDB.hs`, uncommitted):
   severity of `PerasVoteDB`, `PerasCertDB` and `ObjectDiffusion
   Inbound/Outbound` events raised `Info` → `Notice`; the cert‑inclusion
   tracer's namespaces/documentation were rewritten to match the new events
   (`RulesDecision`, `NotEnabledForRound`, `PastHorizonException`,
   `CertInclusionError`).
4. **Testnet** (`testnet/Main.hs`, uncommitted): `setDefaultTraceBackend` also
   sets the root `TraceOptions` severity to `Notice` (backend remains
   `Stdout HumanFormatColoured`; forwarding to `cardano-tracer` is what
   produced the JSON logs).
5. `testnet/Stake.hs` has debug `print`s and a `launch.sh` has a commented
   `redistribute-stake` line — debugging only.

### 6.5 Other testnet‑side changes in the working tree

* `vanilla.yaml`: six equal SPOs replaced by the 8:4:2:1:1 stake groups;
  epoch length 180 → 360.
* `Qry.hs` (`ERelSlotToPerasRoundNo`, in the "TMP magic changes" commit): a
